Audience: maintainer verification.

Verified 2026-09-25 and 2026-09-26 on macOS arm64 with `GitHub Copilot CLI 1.0.88`.
The [adapter reference](../../.agents/skills/harness-adapters/references/harness/copilot.md) owns operating facts; executable owners carry launch and state mechanics.

## Observed vendor surfaces

`copilot --version` printed `GitHub Copilot CLI 1.0.88.`, including when run through a configured launch command that prints its own lines first.
`--help` lists `-i, --interactive <prompt>`, `--plugin-dir <directory>`, `--allow-all`, `--no-ask-user`, `--model <model>` (with `auto`), and `--reasoning-effort <level>` with `none, minimal, low, medium, high, xhigh, max`; it no longer lists the `--effort` alias that 1.0.68 printed beside `--reasoning-effort`.
`copilot help environment` documents that `COPILOT_ALLOW_ALL` set to exactly `true` also trusts the working directory.

A probe plugin mounted with `--plugin-dir` logged this ordered sequence for a tool-using turn launched with `-i`:

```text
userPromptSubmitted
sessionStart
preToolUse
postToolUse
agentStop stopReason=end_turn
```

Hook commands ran with the plugin directory as their working directory, inherited the launch environment, and received `COPILOT_PROJECT_DIR` set to the workspace.
`/exit` fired `sessionEnd` with `reason=user_exit` and printed `copilot --resume=<session-id>`.
The same plugin shape and `COPILOT_ALLOW_ALL=true` ran a prompt with no trust dialog on the CLI packages that reported `1.0.66-0`, `1.0.69-1`, and `1.0.70-0`, with `userPromptSubmitted` and `agentStop` firing.

A turn in which the model started a background shell and replied without waiting fired `agentStop` while the status row still read `Waiting for background shells · <bytes> esc interrupt`.
When the shell finished, Copilot submitted its own follow-up, which fired `userPromptSubmitted`, a `notification` hook, and a second `agentStop`.

A running turn renders a status row such as `◉ Working · 97 B esc interrupt`; the idle row reads `← open sidebar · / commands · ? help · tab next tab`.
The idle composer is a bare `❯` between horizontal rules with no placeholder text.
One `Ctrl+C` on a running turn marked the running shell tool `Operation aborted by user` and returned the idle row with an empty composer, with no hook firing.
An `Escape` sent through tmux `send-keys` did not cancel the turn, twice in a row.
One `Ctrl+C` on an idle agent rendered `ctrl+c again to exit` and then returned to the idle row.

Without `COPILOT_ALLOW_ALL=true`, a fresh folder stopped on a `Confirm folder trust` box asking `Do you trust the files in this folder?` with options `1. Yes`, `2. Yes, and remember this folder for future sessions`, and `3. No (Esc)`, even with `--allow-all`.

A worker that wrote its own commit message passed `-m "Co-authored-by: Copilot ..."`; the per-task git hooks path stripped it, and the landed commit carried no co-author trailer.

In tmux the pane's foreground process group contained a process whose `ps -o comm=` was the versioned install path ending in `/copilot`, both for plain `copilot` and for a configured launch command.

## Coverage and limits

The portable regression pins anchored liveness, worker-only resolution, the single Ctrl+C interrupt and `/exit`, each delivery signal independently, draft safety, the trust-dialog pairing, configured-command parsing and refusals, the version floor, plugin hook lifecycle with stale-generation rejection, retirement paths, and the generated launch line with and without a configured command.
The live guard checks spawn, trust, autonomy, hooks, turn end, liveness, commit trailers, the idle composer, doorbell steering, slash-skill invocation, idle and busy interrupt, the background-shell follow-up, exit, and the trust-dialog signature.
Herdr, Zellij, Orca, and cmux were inspected through their backend-neutral delivery and key capability surfaces, all of which deliver Ctrl+C, but were not live-tested here.
A keyboard cancellation that bypasses `fm-control` leaves the last busy record until the next hook event.
These worker hooks imply no primary supervision guarantee; [Primary session](#primary-session) owns that evidence.

## Primary session

Verified 2026-09-26 with GitHub Copilot CLI 1.0.88 on macOS arm64, in throwaway homes and scratch repositories on private tmux sockets, never against a live home.
The [adapter reference](../../.agents/skills/harness-adapters/references/harness/copilot.md#primary-integration) owns the operating facts these observations support.

### Hook surface

A scratch repository with probe hooks in `.github/hooks/*.json` and in `.claude/settings.json`, run with `COPILOT_ALLOW_ALL=true` so the folder was trusted, showed:

| Question | Observed |
| --- | --- |
| Does Copilot load `<git root>/.github/hooks/*.json`? | Yes, in a trusted folder, including when started from a subdirectory. |
| Where do hook commands run? | With the git root as their working directory and `COPILOT_PROJECT_DIR` naming it by its physical path; the hook's inherited `PWD` kept the launching shell's spelling when Copilot was started at the root. |
| What does `agentStop` receive? | `sessionId`, `timestamp`, `cwd`, `transcriptPath`, `stopReason` (`end_turn`), and `stop_hook_active`. |
| Can `agentStop` continue the agent? | Yes: stdout `{"decision":"block","reason":...}` made Copilot submit the reason as the next prompt, and the following stop carried `stop_hook_active: true`. |
| Does `sessionStart` reach model context? | Yes: its `additionalContext` answered a question about a token only the hook supplied; an interactive session fires it when the first prompt is submitted, with `source` `new`. |
| Does Copilot run `.claude/settings.json`? | Yes, every entry, with Claude-shaped payloads (`hook_event_name`, `session_id`, and for `Stop` `transcript_path` and `stop_hook_active`; `PreToolUse` maps the shell tool to `Bash` with `tool_input.command`). |
| Does a Claude-shaped `PreToolUse` exit 2 deny? | Yes: the tool call reported `Denied by preToolUse hook: hook exited with code 2`. |
| Does a Claude-shaped `Stop` exit 2 block? | No: Copilot displayed the stderr text and ended the turn. |
| Does Claude-shaped `SessionStart` stdout reach model context? | No. |
| Which process starts hooks and tools? | The Copilot executable, as their direct parent; a tool command runs as `bash -c` under it. |

The shell tool reported `initial_wait` as 30 to 600 seconds, which is why the protocol never uses the synchronous mode for the arm, and `mode: "async"` with `detach` omitted as attached to the session across later turns.

### Live primary loop

A firstmate primary in a throwaway home, started as `COPILOT_ALLOW_ALL=true copilot --allow-all`, showed each step of the rendered protocol working together:

- The tracked `sessionStart` hook took the fleet lock as the Copilot process and returned the digest as `additionalContext`; on this machine session start exceeded its own 120s bound, and the model finished the digest itself as the truncation banner instructs.
- The model armed `bin/fm-watch-arm.sh` in `mode: "async"`, collected `watcher: started` with one `read_bash` using the rendered delay, answered, and ended the turn; `agentStop` allowed it with the watcher healthy.
- While the arm ran, the idle row read `Waiting for background shells · 1.4 KiB esc interrupt`, and a captain prompt was answered at once.
- When the watcher delivered a wake the arm exited, Copilot submitted `<system_notification> Shell command "..." (shellId: 1) has completed successfully.` as a new turn, and the model drained, acknowledged, and re-armed.
- With work in flight and no watcher, a turn end blocked, the reason arrived as a user message beginning `U+2063 FIRSTMATE_OP: v1 turn-end-guard:`, and the model re-armed in `mode: "async"` before ending the next turn.
- A message typed into the idle pane through tmux kept its leading U+2063, so a typed away-mode escalation stays distinguishable from the captain without a record-backed doorbell.
- A block decision returned while any background shell was still running was held in Copilot's `Queued` list and delivered only after that shell completed and Copilot's completion turn ran; a captain prompt typed meanwhile was answered at once.
- A synchronous drain that outlived its 30-second `initial_wait` continued in the background, and a model that ended its turn then was blocked correctly, which is why the protocol asks for an `initial_wait` long enough for supervision commands to finish.
- With the model on `auto`, a routed model whose context had just been compacted twice mishandled the forced turn, once bundling a `cd` onto the arm (which the seatbelt denied) and once ignoring it; the repair line names the exact standalone command for that reason.

An earlier run anchored the hooks on `COPILOT_PROJECT_DIR` alone, in a home reached through macOS's `/var` symlink: the digest rendered the physical path, the seatbelt denied the model's arm command spelled with it, and `agentStop` read the healthy watcher as down because the watcher lock records paths as strings.
The registrations now prefer the session's own spelling, and `tests/fm-copilot-primary.test.sh` pins both the anchor and that failure.
